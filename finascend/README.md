# FinAscend

Liquidity-management engine for small businesses. The headline metric is
**Runway-at-Risk (RaR)** — the liquidity analogue of Value-at-Risk:

> *95% RaR = 42 days* means a 5% chance of hitting zero cash within 42 days.
> *CRaR = 36.6 days* is the average runway across that bad tail.

The organizing principle throughout: **a method is only worth what its
validation is worth.** Where a result is negative or inconvenient, it is
reported as measured — see [Results reported against interest](#results-reported-against-interest).

## Quick start

### 1. Backend (required for everything)

```bash
cd backend
python -m venv ../.venv                      # Python 3.12
../.venv/Scripts/python -m pip install -r requirements.txt

# tests (92: statistical correctness + OCR integration)
../.venv/Scripts/python -m pytest tests -q

# API — interactive docs at http://127.0.0.1:8000/docs
../.venv/Scripts/python -m uvicorn app.main:app --reload
```

On Linux/macOS substitute `../.venv/bin/python` throughout.

### 2. Frontend

```bash
cd frontend
npm install
npm run dev                                  # http://localhost:3000
```

The backend must be running: **every number on every page is fetched live**.
There are no fixtures and no fallback values anywhere in the frontend — if the
API is down, pages render an error explaining how to start it rather than
degrading into plausible-looking figures. Point elsewhere with
`NEXT_PUBLIC_API_BASE=http://host:port/api/v1`.

### 3. Regenerate the reports

```bash
cd backend

# Backtest -> BACKTEST_REPORT.md + BACKTEST_REPORT.json (~25 min).
# The JSON is what the frontend's charts read, so the dashboard and the
# report cannot disagree — neither is transcribed by hand.
../.venv/Scripts/python -m app.services.backtesting.run_backtest \
    --step-days 21 --output ../BACKTEST_REPORT.md

# OCR accuracy -> OCR_ACCURACY.md (~4 min; downloads EasyOCR weights once)
../.venv/Scripts/python -m app.services.ingestion.accuracy_report \
    --n-per-tier 24 --output ../OCR_ACCURACY.md
```

**First OCR run needs network access** to fetch the EasyOCR detector and
recognizer weights (~98 MB) into `~/.EasyOCR/model/`. If that host is blocked,
set `FINASCEND_OCR_ENGINE=tesseract` and install the Tesseract binary — the
trade-off is written up in `QUANT_METHODOLOGY.md` §6b.

## Results reported against interest

These are the reason to trust the rest. All three are in the generated reports,
not buried in an appendix.

### 1. The LP optimizer did not beat the naive rules baseline

Over 49 replayed decision points:

| Strategy | Realized penalty | vs rules | Over-commitment |
|---|---:|---:|---:|
| `rules_baseline` | 1,582,964 | — | 18/49 |
| `lp_optimizer` | 1,599,803 | **+1.1%** | 19/49 |
| `dp_knapsack` | 1,600,372 | +1.1% | 19/49 |
| `chance_constrained` | 3,477,827 | +119.7% | **0/49** |

The LP solves the allocation *exactly* — against a *forecast* of available
cash. When that forecast is optimistic it commits money that never arrives.
Solving the wrong problem precisely proved worse than solving roughly the right
problem approximately: the greedy baseline is myopic, but its myopia leaves
slack that absorbs forecast error. An independently written knapsack DP lands
within a rounding error of the LP on both columns, which is what shows this is
a property of optimizing against an uncertain forecast rather than a bug in one
solver. **None of the four dominates**, and the engine reports all four rather
than silently picking the most sophisticated.

### 2. The prediction intervals were overconfident — diagnosed, then fixed

Previously **85.1%** empirical coverage against a 95% nominal level. The
diagnosis was written down before anything changed, and it overturned the three
causes this project had previously suspected:

- **Not** the structural break (pre 86.7% vs post 84.5%).
- **Not** point-forecast bias (mean standardized residual −0.006).
- **Not** parameter uncertainty — SARIMAX's analytic intervals were *already
  honest* at 96.0% coverage on 74% of pairs.

The entire shortfall lived in the 26% of steps that selected Holt-Winters,
which used a different construction: per-horizon quantiles of **five**
walk-forward residuals. That has a hard coverage ceiling of (n−1)/(n+1) = 66.7%
and could never have expressed 95%. It measured 57.2%.

| | before | after | configuration |
|---|---:|---:|---|
| pooled coverage | 85.1% | **95.6%** | 21-day steps, 4,410 pairs — the published backtest |
| pooled coverage | 85.9% | 95.4% | 14-day steps, 6,570 pairs — the diagnostic replay |
| `sarimax` branch | 96.0% | 96.1% | ” |
| `holt_winters` branch | 57.2% | 93.0% | ” |
| width ratio h=90 vs h=14 | 1.0000 | 1.23 | ” |

The per-branch split needed a denser replay than the published backtest runs,
so it is quoted on its own configuration rather than mixed into the first row.

Fixed by normalized split conformal. The intervals genuinely are wider now —
they had to be — and what separates that from arbitrary inflation is that the
multiplier is *measured* from held-out error rather than tuned against the
coverage target, that it lands within a few percent of the value a correctly
specified model needs anyway (mean q̂/z = 1.04 for SARIMAX, 1.05 for
Holt-Winters, where z = 1.96), and that coverage is now flat across the horizon
— every band within a point of nominal — where blanket widening would
over-cover short horizons to rescue long ones.

> **A correction.** An earlier version of this README claimed q̂ came out
> ≈1.0 for SARIMAX and ≈2.3 for Holt-Winters, and read that as the two branches
> being treated differently. That was a units error: q̂ multiplies a *standard
> deviation*, so its reference is z = 1.96, not 1.0. Measured, both models sit
> at q̂ ≈ 2.05, i.e. q̂/z ≈ 1.04. The corrected reading is above.

**Still unfixed:** interval width is constant across weekdays while volatility
is not, visible as over-coverage at weekends.

### 3. OCR degrades sharply, and the field that matters fails unsafely

| Tier | vendor | invoice no. | date | total | all four |
|---|---:|---:|---:|---:|---:|
| clean | 100.0% | 91.7% | 100.0% | 95.8% | 87.5% |
| moderate | 100.0% | 83.3% | 100.0% | 95.8% | 83.3% |
| hard | 75.0% | 12.5% | 33.3% | **50.0%** | 4.2% |

Worse than the headline: on the HARD tier `invoice_number` *declined* 21 of 24
times and was wrong 0 times, while `total_amount` declined 0 times and was
**wrong 12 times**. The field the ledger depends on is the one that never
admits defeat. The normalizer therefore refuses to build a record when a
required field is unreadable, and cross-checks the total against the tax line;
the HARD tier should route to human review rather than into the ledger.

## Selected measured results

- **Parameter recovery.** MLE recovers the generator's known Gamma delay
  parameters to 5.3% mean relative error.
- **Monte Carlo convergence.** On a continuous estimand, SE vs N has a log-log
  slope of −0.43 on average across ten seeds (single-seed range −0.34 to −0.60)
  against a theoretical −0.5 — consistent with O(N^{-1/2}) once the noise in the
  slope estimator is accounted for. On the *discrete* RaR estimand the measured
  slope is −0.321, because a tied integer quantile's bootstrap SE floors out
  rather than decaying smoothly. Both are reported, per configuration, in
  `QUANT_METHODOLOGY.md` §2 — an earlier single figure of −0.517 did not
  reproduce.
- **Dependence matters.** Independent sampling reported RaR = 28 days where the
  fitted copula reported 19 — independence overstates runway by 47%.
- **Correlation recovery is configuration-dependent.** True ρ = 0.72 recovers as
  0.739 (1500d/10cp) or 0.527 (1095d/12cp); the ragged-array bug collapses it to
  0.169. Each configuration is pinned by its own test, because a single quoted
  number without its configuration is how a stale figure survives.
- **Copula PIT.** Marginals are checked per family (Gamma / Weibull /
  Log-normal) independently of the correlation test, and a mutation test proves
  the check has teeth: it rejects latent normals used directly as delays while
  the correlation test still passes on them.
- **DP complexity.** The divisible-item transition was rewritten from O(n·C·k)
  to **O(n·C)** using a sliding-window maximum — minutes to milliseconds.
- **Credit risk.** GBM ROC-AUC 0.654 vs logistic 0.583 vs rules baseline 0.505,
  with calibration tracking closely. Accuracy is never reported: at a ~15%
  default rate, "never defaults" scores 85% while being useless.
- **Chance constraint.** Achieved shortfall probability lands exactly on ε
  (0.200 / 0.100 / 0.050 / 0.010), with a monotone risk-penalty frontier.

## Frontend design

Five pages, all live: Overview (RaR/CRaR, forecast fan, MC standard error),
Solver comparison, Credit risk, OCR ingestion, Backtest report.

Dark by commitment rather than as a variant. The four categorical hues —
amber, teal, violet, rose — were **machine-validated** against the `#11151a`
chart surface in OKLab across protan/deutan/tritan simulation, not chosen by
eye: worst all-pairs CVD ΔE 8.8 (target ≥ 8) and normal-vision ΔE 16.1 (floor
≥ 15), all four inside the L 0.48–0.67 band and above 3:1 contrast. Series
colour is bound to a *strategy*, never to its rank, so a chart that drops a
series never repaints the others. Every figure is JetBrains Mono with
`tabular-nums`. The palette and the 1.25 type scale are stated at the top of
`frontend/app/globals.css`.

## What is deliberately not implemented

`/graph/*`, `/chat`, `/voice/*` return **HTTP 501** with a stated reason. They
route, authenticate and validate correctly, but nothing behind them is faked —
no canned text, no placeholder numbers. Decentro/Plaid ingestion, Postgres,
Celery and Graph RAG are likewise absent rather than stubbed.
